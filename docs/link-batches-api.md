# Multi-file Link batches

Discovery advertises `features.fileBatches`. The recipient must have both `file.receive` and `file.batch.receive` approved during pairing; do not silently expand an existing approval. Existing single-file transfers remain compatible. All endpoints use the paired device bearer credential and `share.relay`. Device ownership, revoked credentials, disabled accounts and explicit household-sharing opt-in remain enforced. A package is addressed to one device, not every device in an account.

## Sender

1. Calculate SHA-256 locally for each file. POST `/api/link/mobile/share/batches` with `{targetDeviceId, requestKey, files:[{filename,mimeType,size,sha256}]}`. Persist an optional `requestKey` (1–40 ASCII letters/digits/underscore/hyphen, such as a UUID) before the request; retries with the same key and manifest recover the same package after a lost response. Reusing a key with a changed manifest is rejected. Between 1 and 100 files are allowed; each file obeys the server file limit. The response `{batch}` contains stable file IDs, normalized portable names, status, expiry and progress. Manifest names are flat, UTF-8 bounded, case-insensitively unique and exclude Windows reserved names. Never change the manifest after creation.
2. For each manifest file, POST `/api/link/mobile/share/uploads` with its normalized `filename`, `mimeType`, `size`, the same `targetDeviceId`, and `batchFileId`. Use the existing encrypted resumable upload protocol. Repeating this request returns the same upload ID and current offset. Only three files may upload concurrently. Upload at the returned offset; query the upload status after a reconnect.
3. Finalize each upload using the existing upload POST. The server verifies the uploaded SHA-256 against the immutable manifest (422 on mismatch), attaches it to the batch, and emits **no individual share offer**. The response includes `transferId`, `sha256`, `batchId`. A mismatched file cannot be published; cancel that upload and restart its bytes. A changed source file needs a new batch/manifest.
4. POST `/api/link/mobile/share/batches/{id}` with `{action:"publish"}` after all files finalize. Publication is atomic and retry-safe. It creates exactly one `share.offer` event with `{type:"file.batch",batchId,fileCount,totalBytes,sourceName,sameAccount}`. The payload contains no download credentials or file contents. Do not offer files individually as a fallback after publication.

GET `/api/link/mobile/share/batches/{id}` returns `{batch}`. GET `/api/link/mobile/share/batches` returns the latest 50 unexpired authorized batches, newest first, including accepted packages. Incoming assembling drafts are omitted from the list. Poll the individual ID for older retained transfers; native clients must persist batch IDs locally. After reconnect, consult this list as well as heartbeat events: the normal offer-event retention window is shorter than the package lifetime. Acknowledging a heartbeat event does **not** accept or reject a package.

## Recipient

Fetch the manifest, show one confirmation for the entire package, then POST `{action:"accept"}` or `{action:"reject"}`. Only the addressed recipient can decide; neither the sender nor another device on the same account can consent. Repeated identical decisions are harmless; changing a rejected decision is disallowed. Files are not downloadable until acceptance. Approved account/household access is checked again during downloads.

After acceptance, each manifest file has a `downloadUrl` under the paired server. Use bearer authentication only to that verified server; follow the existing streamed file download contract. Choose one destination directory for the package, never a new chooser per file. Persist the user's selection and package consent. Download into uniquely named temporary files, hash while streaming, validate exact `size` and `sha256`, then publish atomically without replacing an existing user file. The server-normalized manifest names do not authorize overwriting an existing local file or following a symlink. Clients must resolve local collisions themselves.

Optionally POST `{action:"progress",fileId,bytes}` at a throttled rate (no more than every few seconds per package) while downloading. Progress is recipient-reported and never proof of integrity. It can decrease when restarting an incomplete file. POST `{action:"received",fileId,size,sha256}` only after successful verification and durable local save. Receipts are idempotent, persist across restarts and set the package to `completed` once every file is acknowledged. The sender can read aggregate and per-file upload/download progress. `receivedBytes` counts receipted files only; `downloadedBytes` includes unverified recipient progress.

## Recovery, cancellation and retention

Statuses: `assembling → offered → accepted → completed`, or recipient `rejected` / sender `canceled`. Sender cancellation is accepted while assembling, offered or accepted; further downloads are denied. It cannot revoke already saved bytes or an already opened stream. The recipient cannot change sender metadata or cancel uploads.

All batch metadata and encrypted files expire 24 hours after creation. Expired/canceled/rejected packages cannot be opened or accepted. Rejection/cancellation immediately discard finalized encrypted files and expire pending uploads; repeating the same decision retries cleanup safely. Normal expiry uses existing transfer cleanup. Temporary chunks retain the existing bounded cleanup policy. No unencrypted archive or ZIP copy is created. Completed receipts remain available until package expiry to recover after a lost HTTP response. Use GET to restore state rather than requesting another consent; skip verified locally saved files, retry missing ones. Clients must still verify their local files before skipping them if local state was lost or modified.

Uploads resume at chunk boundaries. A crashed finalization lease is recoverable after one hour through upload status/finalization retry. If finalization already attached a file before the response was lost, its batch manifest shows it ready; do not start another upload. Interrupted downloads currently restart **that file**, not the package; byte-range download resumption is not advertised. Persist verified receipts and temporary-path cleanup locally. Never automatically execute a received file.

Run `node scripts/run-plant-tests.mjs batches` for isolated encrypted-storage/database integration checks and `npm test` for manifest and progress tests. No production database or external notification service is used.
